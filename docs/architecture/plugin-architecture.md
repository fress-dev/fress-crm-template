# プラグイン設計方針

> **最終更新:** 2026-06-10  
> 現時点で**実装する範囲**と、将来の拡張の置き場所を定義する。  
> コア非変更の原則は [AGENTS.md](../../AGENTS.md) に従う。

## 層の名称

| 英語 | 日本語 | 旧称（参考） |
|------|--------|-------------|
| **Core** | コア | Platform |
| **Plugin** | プラグイン | 機能プラグイン・連携プラグイン |
| **Tenant Config** | テナント設定 | 顧客設定 |
| **Custom Layer** | カスタム層 | 顧客拡張 |

```
Core（常時）
  + Plugin（0〜複数）
  + Tenant Config（必須）
  + Custom Layer（必要なときだけ）
```

## 基本方針

- **業界パック（不動産一式・美容一式）は作らない。**
- **コアを土台に、必要なプラグインだけ載せる。**
- 店舗差は **テナント設定**（`tenants/<顧客>.json`）で吸収する。コードにしない。

## 今すぐ必要なもの

> **実装時の優先:** [AGENTS.md](../../AGENTS.md) の「ディレクトリ規約」が正。platform 移行 PR までは **すべて `src/custom/**`**。以下は将来の目標レイアウト。

| 層 | 今やること | 置き場所（現状 → 将来） |
|----|-----------|------------------------|
| **コア** | プラグインレジストリ、`App.tsx` からの組み立て、カスタム層用の契約（型） | 現状: `src/custom/**` → 将来: `src/platform/**` |
| **テナント設定** | 有効プラグイン一覧、フォーム追加項目、商談段階、カスタム層参照 | 将来: `tenants/<顧客>.json` |
| **プラグイン** | 最初の1本は要件が出たとき（例: 予約） | 現状: `src/custom/**` → 将来: `src/plugins/<機能名>/**` |

## 今は不要（設計だけ頭に置く）

| 対象 | 理由 |
|------|------|
| **連携系プラグイン** | 顧客が外部連携を要するまで。最初はカスタム層 or 汎用 Webhook で足りる |
| **テナント設定のひな形** | 新規顧客用のコピー元 JSON。顧客が増えてからでよい |
| **業界パック** | 採用しない |

## 各層の定義

### コア（常時・1つ）

- atomic-crm の CRM（担当者・商談・メモ・タスク等）は触らない
- プラグイン登録 API・テナント設定の読み込み・日本語/JST
- **業務画面・業界固有ドメインは入れない**

### プラグイン（0〜複数）

- コアに後から足す**コードの単位**。業務・連携ともにプラグインと呼ぶ
- **1機能＝1プラグイン**。業界名は付けない（`appointments`、`properties` など）
- 申し込みの**型・フロー・画面**が別物のときだけ別プラグインにする
- フォームは固定せず、テナント設定から追加項目をマージできる拡張ポイントを持つ
- 連携（Webhook・外部 API）は将来、同じくプラグインとして追加する

### テナント設定（必須）

- その顧客の本番設定
- 入れるもの: 有効プラグイン、追加項目、表示/非表示、商談段階、連携 URL・鍵（将来）
- **ビジネスロジックは書かない**
- 新規導入時は任意のひな形 JSON をコピーして作成してよい

### カスタム層（必要なとき）

- テナント設定では足りない独自処理
- プラグインが定義する **Extension インターフェースを実装**して差し込む
- プラグイン本体の継承・複製はしない
- 例: `extensions/tenant-b/appointments.ts` をテナント設定から参照

## プラグインの有効化・停止・削除

### 管理方法（現状）

| 操作 | やること | 自動？ |
|------|----------|--------|
| **有効化** | `tenants/<id>.json` の `plugins` に id を追加 → **追加 migration を適用**（`make dev` / `supabase db push` 等） | migration は手動実行 |
| **停止（通常の OFF）** | `plugins` から id を外す → アプリ再起動 / 再読み込み | JSON のみ。DB は触らない |
| **強制削除** | 誤導入・完全撤去が必要なときだけ、**別 PR の teardown migration** でテーブル・カラムを DROP | 人間が判断して migration を書き・実行 |

**将来:** テナント設定画面から ON/OFF できる UI を用意する想定。**現状は JSON 編集のまま**でよい。

JSON を変更したあと、有効化・強制削除に伴う migration は**人間が実施**する（JSON のトグルだけでは migration は走らない）。

### 三つの状態

```
有効 ──(plugins から外す)──► 停止 ──(teardown migration + 判断)──► 強制削除済み
  ▲                              │
  └── plugins に戻す + migration  │  通常はここで止める
      （再有効化）                └── DB スキーマ・データは残る
```

| 状態 | 機能（UI・API） | DB（テーブル・カラム・データ） |
|------|----------------|-------------------------------|
| **有効** | プラグイン画面・拡張が動く | 追加 migration 済み |
| **停止** | `isXxxPluginEnabled()` が false → **コアにフォールバック** | **そのまま残す**（nullable 推奨）。コア CRUD は壊さない |
| **強制削除** | コード・register からも外す（別作業） | **DROP migration で削除**（データ消失を承知） |

**原則:** 一度有効にしたプラグインは、**通常は「停止」まで**。カラム削除はデータが消えるためデフォルトでは行わない。間違えて入れた・本当に不要、といった**例外**だけ強制削除（teardown migration）を検討する。

### migration の考え方

- **有効化用:** `supabase/migrations/` に**追加のみ**。`PluginDefinition.migrations` にファイル名を列挙（参照用。実行は Supabase の通常フロー）。
- **停止用:** 原則 **migration 不要**。実行時ガードで機能だけ止める。
- **強制削除用:** 新規 forward migration で `DROP TABLE` / `DROP COLUMN`、view 再作成、FK 解除などを**明示的に**書く。過去 migration の編集・削除はしない。
- プラグインが触った **コアテーブルのカラム**（例: `contacts.store_id`）は、停止可能にするため **DB `NOT NULL` にしない**。必須はプラグイン有効時の UI バリデーションで行う。

### 実装側の約束（停止時にコアを壊さない）

- プラグイン固有 UI は `isXxxPluginEnabled()` でガードし、無効時はコア実装へフォールバックする。
- `dataProvider` 拡張・シード・ナビは有効時のみ。
- 依存は `PluginDefinition.dependsOn` で明示（例: 予約が stores 必須）。

## 差分の置き場所

| 違い | 対応 |
|------|------|
| 項目の有無・ラベル | テナント設定 |
| 申し込みの型・フローが違う | 別のプラグイン |
| 外部連携（将来） | 連携プラグイン → 当面はカスタム層 |
| 独自ロジック | カスタム層 |
| 本体ごと別物 | 例外（有償カスタム） |

## 導入例

| 顧客 | 構成 |
|------|------|
| 代理仲介（物件なし） | コア + テナント設定のみ |
| 物件管理＋内見 | コア + `properties` + `appointments` + テナント設定 |
| 依頼型申し込み | コア + `service-requests` + テナント設定 |

## 実装順序

1. コア — レジストリ + テナント設定の型 + Extension 契約
2. テナント設定の読み込み（1社分の JSON でよい）
3. プラグイン1本（要件が確定してから）
4. カスタム層（最初の例外要件が出たとき）
5. 連携プラグイン・テナント設定のひな形（顧客・連携が増えてから）
